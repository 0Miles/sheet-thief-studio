# 團譜 schema：小節序列全域共用，合併粒度到拍點

團譜文件的結構決定了「兩個人同時改」會得到什麼，而且文件一旦有資料就很難改形狀。我們的選擇：

- **小節序列是全域的。** `bars` 是一張以小節 id 為鍵的表，順序由每個小節的排序鍵（fractional index）決定；拍號、速度、反覆記號記在小節上。每個聲部只存「某個小節 id 的內容」。這樣「所有聲部的小節數相同、拍號一致」由結構保證，不需要事後檢查，也不需要 Yjs 的 move。
- **合併粒度到拍點。** 一個聲部在一個小節裡，每條聲線是一個 `Y.Array`，元素是拍點（`Y.Map`）；拍點裡的音符以位置為鍵（弦樂是弦、鼓是鼓件、五線譜是音高），值是整顆替換的 JSON。

  結果是：兩人同時在同一小節插入拍點會合併，各自連續輸入的拍點保持成段；同一拍點上不同弦的音會合併；同一個音符的同時修改是後寫者勝。
- **以位置為鍵的音符讓「一拍一弦最多一個音」成為結構。** 沒有音符的拍點就是休止，不存在「休止又有音」的狀態。
- **跨小節的連結不存 id。** 連結線記在目的音上，滑音、搥弦記在起點音上，投影時沿同一條弦或同一個音高去找對象；找不到就標記。

考慮過、沒採用的做法：

- **整個小節內容當成一個後寫者勝的值。** 實作最簡單，但兩人同時改同一小節時，一方的修改會無聲地消失。
- **拍點用純 JSON、以排序鍵排序。** 同時輸入的拍點會彼此交錯，譜面變成亂的；同一拍點的同時修改還會產生重複的拍點。
- **音符也做成可合併的 `Y.Map`。** 同一個音符同時改格號和技巧可以合併，但文件大小和複雜度明顯增加；這種衝突很少見，後寫者勝可以接受。

## Consequences

- 小節內容的時值和拍號不符、懸空的連結線，都只做標記；客戶端不自動修復，避免多個客戶端互相修來修去。
- 建立小節的人要在同一筆交易裡替所有聲部建好內容容器，建立聲部的人要替所有小節建好；缺漏只由伺服器補齊，避免兩端同時建立而互相覆蓋。
- 文件帶 `schemaVersion`；伺服器在載入時遷移，客戶端遇到比自己新的版本就以唯讀開啟。
