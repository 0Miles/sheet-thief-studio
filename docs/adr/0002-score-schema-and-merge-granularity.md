# 團譜 schema：小節序列全域共用，合併粒度到拍點

團譜文件的結構決定了「兩個人同時改」會得到什麼，而且文件一旦有資料就很難改形狀。我們的選擇：

- **小節序列是全域的。** `bars` 是一張以小節 id 為鍵的表，順序由每個小節的排序鍵（fractional index）決定；拍號、速度、反覆記號記在小節上。每個聲部只存「某個小節 id 的內容」。這樣「所有聲部的小節數相同、拍號一致」由結構保證，不需要事後檢查，也不需要 Yjs 的 move。
- **合併粒度到拍點。** 一個聲部在一個小節裡，每條聲線是一個 `Y.Array`，元素是拍點（`Y.Map`）；拍點裡的音符以位置為鍵（弦樂是弦、鼓是鼓件、五線譜是音高），值是整顆替換的 JSON。

  結果是：兩人同時在同一小節插入拍點會合併，各自連續輸入的拍點保持成段；同一拍點上不同弦的音會合併；同一個音符的同時修改是後寫者勝。
- **以位置為鍵的音符讓「一拍一弦最多一個音」成為結構。** 沒有音符的拍點就是休止，不存在「休止又有音」的狀態。
- **跨小節的連結不存 id。** 連結線記在目的音上，滑音、搥弦記在起點音上，投影時沿同一條弦或同一個音高去找對象；找不到就標記。

考慮過、沒採用的做法：

- **整個小節內容當成一個後寫者勝的值。** 實作最簡單，但兩人同時改同一小節時，一方的修改會無聲地消失。
- **拍點用純 JSON、以排序鍵排序。** 同時輸入的拍點會彼此交錯，譜面變成亂的；同一拍點的同時修改還會產生重複的拍點。
- **音符也做成可合併的 `Y.Map`。** 同一個音符同時改格號和技巧可以合併，但文件大小和複雜度明顯增加；這種衝突很少見，後寫者勝可以接受。

## Consequences

- 小節內容的時值和拍號不符、懸空的連結線，都只做標記；客戶端不自動修復，避免多個客戶端互相修來修去。
- 建立小節的人要在同一筆交易裡替所有聲部建好內容容器，建立聲部的人要替所有小節建好；缺漏只由伺服器補齊，避免兩端同時建立而互相覆蓋。
- 文件帶 `schemaVersion`；伺服器在載入時遷移，客戶端遇到比自己新的版本就以唯讀開啟。

## 增補（2026-11-13）：完整的形狀、遷移、讀取時容錯，與兩條同時修改的規定

M1a–M5 的設計對質把文件的完整形狀一次定下。上面的原文不改，以下是增補。

- **完整的形狀寫在 [`docs/spec/schema.md`](../spec/schema.md)。** 程式裡唯一的真相是 `packages/score-model` 的 zod schema；TypeScript 型別由它推出，`packages/contracts` 只 re-export。理由：版本 JSON 的驗證、匯入的驗證、遷移都在 score-model 裡，而 score-model 是前後端共用、沒有 DOM 的套件，不應反過來依賴 contracts。
- **小節內容的容器預先建好每一條聲線**（補充）。建立小節或聲部的人，在同一筆交易裡替聲部每個譜表建好兩條聲線的 `Y.Array`；伺服器的 `fillMissingContent` 也補齊缺少的聲線。理由同上面的 Consequences：兩個人同時「第一次寫進第二聲線」時，各自建立的 `Y.Array` 會互相覆蓋，一方的拍點無聲消失。
- **加法欄位不升版。** 新增 optional 欄位屬於加法改動，不升 `schemaVersion`；條件是同一個 PR 也改 `docs/spec/schema.md`、這份增補（形狀有變時）與 zod schema，不需要開設計會議。讀到不認得的欄位一律忽略並原樣保留：改寫音符的指令以儲存的原值為底，不以 zod 解析後的值為底，否則舊分頁會把新欄位刪掉。非加法的改動（升 `schemaVersion` 並加遷移）不由 agent 自行決定，要開 `ready-for-human` 票。
- **遷移做兩面。** `Y.Doc` 由伺服器在 `onLoadDocument` 時以參與者身分遷移（不在 `onStoreDocument` 裡改文件，否則會再觸發一次儲存）。版本存的是 `docToJson` 的結果，帶著當時的 `schemaVersion`；讀取或還原舊版本之前，先跑 JSON 遷移。兩面的遷移放在 score-model 的同一份清單裡，各自用舊版 fixture 測試。完整 schema 發布時是 `schemaVersion: 1`（M0 沒有持久化任何文件）。
- **讀取時容錯，伺服器不檢查更新的內容。** Editor 視為可信任：伺服器只靠 readOnly 連線與訊息大小上限把關。`docToJson` 對每個拍點與音符 `safeParse`，讀不懂的略過、記成 `invalidContent` Flag，永遠不丟例外；小節的拍號讀不懂時當成 4/4，聲部的種類讀不懂時整個聲部略過。驗證結果以拍點的 `Y.Map` 為鍵快取在 `WeakMap` 裡，只重新驗證變動的小節（不快取時 4,000 個拍點要 6.5 ms，是 `docToJson` 本身的 3.6 倍）。伺服器端的讀取用同一個函式。
- **規定一：刪除小節時，同時送到那些小節的輸入會消失。** 這是「不讓修改無聲消失」的明確例外。刪除小節不跳確認對話框，可以復原；復原能救回刪除當下的內容（Yjs 在同一筆交易裡刪除父節點與子節點），之後別人送到的拍點不保證會回來。刪小節是常見的小動作，為它加確認或保留孤兒內容都不值得。這個行為用 vitest 鎖住。
- **規定二：放置樂句與貼上小節段，在既有的 `Y.Array` 上先刪再插。** 兩者都會取代目標小節的內容，但不換掉小節內容的 `Y.Map`，而是在每條聲線既有的 `Y.Array` 上刪除再插入。這樣同時在那裡輸入的人，拍點會留下來（之後可能被標成 overfull），不會無聲消失；換掉 `Y.Map` 正是上面拒絕的「整個小節內容後寫者勝」。
